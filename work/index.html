Data Discovery

Finding an answer across a document archive.

A folder name can tell you where a document was filed. It cannot tell you which paragraph in a PDF answers a question, or whether a related detail is in a spreadsheet or an email.

Data Discovery is a Windows application that inventories a collection, extracts supported content and builds keyword and semantic indexes. Users can search the archive or ask questions, then follow citations to the supporting source material.

Original files remain read-only, and indexing and retrieval always run locally. Asking for a generated answer sends the question and the cited passages only; source files and document paths never leave the machine.

What I built

  • File inventory and document processing
  • Keyword and semantic search indexes
  • Questions answered with source citations
  • Local ONNX embedding, with local or cloud answer generation
  • Saved answers with an evidence ledger and chain of custody
  • Separate indexes and outputs that preserve source files

Technology.NET, C#, SQLite FTS5, ONNX Runtime, Nomic embeddings, LM Studio, OpenAI

Email Archiver

Getting business email to the right archive.

Project correspondence arrives in email, but the record belongs with the work it concerns. Filing it manually becomes difficult to track when many work units and destinations are involved.

I developed an archiving application that identifies work-related messages, resolves the work unit and determines the destination. Configurable rules control how messages are delivered to SharePoint or the file system.

Delivery state and failure diagnostics let administrators see what happened to a message. Retry and recovery are included because an interrupted delivery still needs to be accounted for.

Messages are captured into an ingest queue as they arrive, and once delivered a copy is retained in Azure Blob Storage. That retained copy is independent of the mailbox the message came from and of the server that files it, so deleting the original, or losing the server, does not lose the record.

Filing only matters if the message can be found again. Every archived message keeps its sender, subject, dates and work unit, so it can be located without opening a mailbox. Messages delivered to SharePoint carry those same details as metadata columns, so they sort and filter there like any other document.

What I built

  • Rules for identifying and routing work-related email
  • Microsoft 365 integration
  • SharePoint and file-system delivery
  • Delivery tracking and failure diagnostics
  • Administrative controls for retry and recovery
  • Ingest queue on arrival, long-term retention in Blob Storage
  • Search by sender, subject, date and work unit
  • SharePoint metadata columns for each delivered message

Technology.NET, C#, Blazor, SQL Server, Azure Functions, Entra ID, Microsoft 365, Microsoft Graph, SharePoint, Service Bus, Queues, Blob Storage

Integration Hub

Making the rules between business systems visible.

Several applications needed to exchange information, but each used its own identifiers, data structures and business rules. A connection between two systems would still need somewhere to define those differences and handle exceptions.

I designed and developed a web application for managing the integrations, alongside services that execute them. Administrators can see the field mappings and transformation rules, configure schedules and review processing status.

Validation and operator review are part of the design. The person running an integration needs to understand what will move, what needs attention and what happened during execution.

What I built

  • Web controls for integration configuration
  • Field mapping and transformation rules
  • Validation and operator review
  • Scheduled and manually triggered execution
  • Processing status and exception handling

Technology.NET, C#, Blazor, SQL Server, Azure Functions, Entra ID, RBAC, ASP.NET Core, REST APIs

Transformer

Knowing what the business must be able to do, and what is missing.

An organization can list its problems and still not know what to do about them. Issues are logged, roadmaps are drawn and analyses are commissioned, but nothing joins them: no one can say which business capability a given issue actually affects, or what has to exist before the organization can perform that capability at all.

Transformer holds that model. A capability is a stable business ability that delivers value, independent of any particular system, and every issue connects through a capability to the domains, processes, systems, data entities, control points and phases required to support it. A capability counts as complete only when all of those are present. Whatever is absent is a gap, counted rather than described.

That makes prioritization an argument about evidence. Gaps are weighed by financial criticality, their number and severity, the degree of architectural support behind them, their dependencies and where they sit in the roadmap, then packaged into initiatives and projects that stay linked to the capability they exist to close. Coverage, gap, traceability and roadmap views answer different questions for different readers, and model health checks surface the breaks: an issue with no capability, a capability with no supporting system, a project belonging to no initiative.

What I built

  • A model connecting domains, capabilities, processes, systems, data entities, control points and phases
  • Issues traced through the capability they affect to the elements supporting it
  • Gap identification wherever a required element is missing, with coverage counted per capability
  • Prioritization by financial criticality, gap severity, architectural support and dependency
  • Initiatives and projects linked back to the capabilities they exist to close
  • Model health checks for missing relationships across the model

Technology.NET, C#, Blazor, SQL Server, Azure Functions, Entra ID, RBAC

ERP reporting platform

Extending a closed ERP without changing it.

Allnorth ran its business on BST10, a cloud-hosted ERP. The system held everything the firm needed to see, but not in a form the business could reach: no interface covered the reporting and the custom applications that finance, the project management office and the field needed. Commissioning changes inside a vendor’s product is a slow way to answer a question that changes every quarter.

So I left the ERP alone and built around it. The vendor delivered a database backup to Azure every four hours, which I restored into an on-premises SQL Server as a read-only copy. A layer of SQL views and procedures over that copy resolved the parts of the schema that mattered, and every application we built kept its own data in its own database on the same server. Nothing we wrote ever posted into the ERP, so the ERP stayed authoritative and everything else stayed free to change.

From there the same consistent copy served spreadsheets, Power BI and custom desktop and web applications. It carried resource scheduling and demand by skill and experience rather than headcount alone, revenue forecasting, and the variance analysis that located where revenue was leaking and margin eroding.

Field time came back the other way. Crews filled in an Excel template, the field LEM for labour, equipment and materials. Its picklists for people, projects, tasks, equipment and living-out allowances were populated by queries against that same offline copy, so the values were already valid before anyone typed them. The completed return was emailed in and dropped onto a desktop application, which checked that the entries were complete, that the contractors named on them were registered in the ERP, and that billing and costing rates existed for them in the separate system that held rates. Only then would it produce the timesheet, vendor invoice and expense files, in the CSV import formats BST10 accepts.

What I built

  • Four-hourly replication of the vendor-hosted database into Azure
  • Restore into an on-premises SQL Server as a read-only copy
  • A SQL view and procedure layer over the replicated schema
  • Application databases alongside it, so no custom software wrote into the ERP
  • Reporting for the project management office, finance and payroll
  • A field time template whose picklists were driven from the offline copy
  • A desktop application that validated field returns against registration and rates
  • Timesheet, vendor invoice and expense files in the ERP’s CSV import formats

Technology.NET, C#, SQL Server, Azure, Power BI, BST10
