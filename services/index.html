Business Analysis

Before choosing software, establish what the business needs it to do. I work with the people involved to map the current process, identify the rules and agree on what a better result would look like.

Those requirements are the basis for evaluating existing applications. I look at what a product covers and where it falls short before recommending whether to buy or build.

  • Current and future workflows, including responsibilities and exceptions
  • Business rules, data flows and acceptance criteria
  • Market assessment, software evaluation and ERP fit/gap analysis

Continuous Improvement

A process can accumulate extra steps over time: a duplicate entry, a spreadsheet check, an email asking someone to confirm a number. I look at why those steps exist and which ones can change.

The review also looks at ownership and controls. A shorter process still needs a clear way to handle mistakes and exceptions.

  • Workflow redesign and removal of duplicate work
  • Data quality, reporting and control points
  • Automation opportunities after the process has been reviewed

Systems Integration

ERP, payroll and project applications often hold different parts of the same record. An integration needs to establish which system owns each field, how identifiers match and what happens when data fails validation.

I design and build connections using APIs, databases and files, with controls for the people responsible for running them.

  • Field mapping, transformations and master-data synchronization
  • Scheduled or event-driven processing
  • Status, exception handling and audit history

Custom Software Development

Custom development begins with a requirement that suitable existing software cannot meet. After assessing the market, I build web and Windows applications for those needs, or develops the missing parts around an existing product.

The scope includes the parts needed to run the application day to day: administration, background jobs, error handling and reporting. Development uses .NET and C#, with SQL Server, APIs and Azure where they fit.

  • Web and Windows applications
  • Database, API and Microsoft 365 integration
  • Data processing, reports and administrative tools

AI Integration

You know AI could help somewhere. You don’t need AI everywhere.

Start with a job worth testing, such as searching an archive or extracting information from documents. The design needs to account for source evidence, human review and where the data is allowed to go.

  • Document search and questions answered with supporting sources
  • Classification, extraction and workflow assistance
  • Local or cloud models chosen around privacy and hosting requirements

Software Modernization

An older application may contain years of business decisions in its screens, SQL procedures and reports. Understanding those rules is part of replacing or changing the software.

I can examine the application and its dependencies, document what must survive, and assess whether an existing product can take over the job. Where a rebuild is needed, we can plan a staged transition using modern .NET, a web interface, an API or database changes.

  • Code, database and dependency assessment
  • Business-rule extraction and a modernization roadmap
  • Rebuilding, data migration and validation alongside the existing system

Before an ERP implementation

An ERP implementation is a business project that happens to involve software. Most of what decides how it goes is settled before anyone configures anything.

Discuss an implementation
Backfill the people you assign to it
The common mistake is expecting someone to run their department and learn a new system at the same time. They cannot give the implementation the attention it needs to work out what the new requirements are, how the data is handled and where the workflows differ, so the project runs long. Then it collides with the vendor’s schedule, and you are asked to finish in three weeks or wait six months while they take on someone else.
Change management is not software training
People are shown how to use the new system and not what has changed about their job. The screens are the easy part. What needs explaining is which decisions have moved, which numbers are now arrived at differently, and what is no longer possible. That includes the people who only read the output: a manager who does not know how the operation runs will read a correct figure as an error and act on it.
Make the new way the only way
Behaviour that is still possible comes back as soon as attention moves elsewhere, so what holds is what was designed in. Remove the option. Validate the value where it is entered rather than correcting it downstream. Provide a legitimate route for the exception, because if there is no sanctioned way to handle the awkward case somebody will invent one, and the spreadsheet they build to get around the system becomes the next system of record.
Migrate less than you think
Bringing across every detail means bringing across the reference data behind it, and with that come old codes and classes that fill the new pick lists with options nobody should be choosing. A new system is the best chance you will get to re-architect the data and close the loopholes people have been working around. It is easier to say a thing is not available here than to ask again that nobody do it.
Program the migration, and keep it out of spreadsheets
An implementation that runs six months means the extract taken in month one is stale by month two. Every extract should come from a query, a view or procedure carrying the transformations and the data quality checks, so the whole set can be rebuilt on demand and tested as often as you like. That is what makes the reconciliations possible: when revenue is calculated one way in the old system and another way in the new one, you cannot prove the two agree across a four-day cutover unless you have been proving it all along.
